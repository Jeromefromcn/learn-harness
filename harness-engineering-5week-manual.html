DAY 3

把它變成完整的循環

~2 hr

真正的 agent 是一個循環(loop):模型調工具 -> 你執行 -> 把結果喂回去 -> 模型繼續,直到它給出最終答案.這是本週的技術核心.

agent loop 骨架 
def run_agent(user_msg, max_turns=6):
    messages = [{"role": "user", "content": user_msg}]
    for _ in range(max_turns):
        resp = client.messages.create(model=MODEL,
                 max_tokens=1024, tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return resp        # 完成,返回最終答案
        # 執行每個被請求的工具,把結果作為 tool_result 返回
        results = dispatch_tools(resp.content)
        messages.append({"role": "user", "content": results})

DAY 5

第一道護欄:結構化輸出校驗

~90 min

用 Pydantic 強制 agent 的最終輸出符合 schema.校驗失敗就當成報錯(下週會接上重試).跨過這一步,你的東西就從 demo 變成"半個產品"了.

guardrail.py 
from pydantic import BaseModel, field_validator

class ShippingQuote(BaseModel):
    fee_hkd: float
    eta_days: int
    @field_validator("fee_hkd")
    def positive(cls, v):
        assert v > 0, "fee must be positive"
        return v

def validate_output(raw: str) -> ShippingQuote:
    return ShippingQuote.model_validate_json(raw)  # 失敗就拋異常

WEEK 03

加上可靠性

本週目標

把上週的 agent 變得"可信".這週的每一項--重試,熔斷,可觀測性,降級,成本控制--你在後端都做過,現在只是把對象換成一個不確定的 LLM 下游依賴(dependency).這是你的主場,可以走快一點.

DAY 1

重試 + 指數退避

~60 min

LLM API 會限流,會超時,輸出偶爾過不了校驗.把這些都當成可重試的瞬時故障來處理.

DAY 2

超時 + 熔斷器

~60 min

避免單次調用卡死整個流程,並在連續失敗時快速失敗,而不是反復去捶一個已經掛了的服務.

DAY 3

可觀測性:每次調用都留痕

~90 min

沒有這一層,你連 agent 為什麼出錯都查不到.記錄足夠的結構化信息,讓每次調用都可追溯,可分析.記住這份手寫的日誌(log)--第五週你會用 LangSmith 把它替換掉,親身對比兩者的差別.

observability.py 
import json, time, hashlib, logging

def log_call(messages, resp, t0):
    logging.info(json.dumps({
        "input_hash": hashlib.sha256(
            json.dumps(messages).encode()).hexdigest()[:12],
        "model": resp.model,
        "latency_ms": int((time.time() - t0) * 1000),
        "in_tokens": resp.usage.input_tokens,
        "out_tokens": resp.usage.output_tokens,
        "stop_reason": resp.stop_reason,
    }))

WEEK 04

學會評估

本週目標

為一個"沒有標準答案"的系統設計測試.這是 harness engineering 裡最反直覺,也最值錢的技能,大多數人停在"會寫 prompt"就不往前走了.慢慢來,這週是你真正拉開差距的地方.

DAY 1

建立評估數據集

~90 min

沒有數據集就沒有評估.用你前兩週的失敗模式清單當靈感,故意把容易出錯的邊界案例放進去.這份數據集(dataset)第五週還會再用一次.

DAY 2

確定性指標:精確率 / 召回率

~90 min

先用便宜,確定性的方式評估能量化的部分(比如"有沒有調對工具""輸出格式對不對")--對應 Fowler 講的計算式 sensor.

DAY 3

推理式 sensor:LLM-as-judge

~2 hr

對"沒有標準答案"的部分(回答質量,語氣,是否答非所問),用一個模型去給另一個模型的輸出打分.理解它的威力,也理解它的不確定性.

judge.py - 打分骨架 
JUDGE_PROMPT = """你是嚴格的評審.根據以下標準給回答打 1–5 分,
只輸出 JSON:{"score": int, "reason": str}
標準:準確性,是否老實承認不知道,是否答非所問.
問題:{q}
回答:{a}"""

def judge(q, a):
    r = client.messages.create(model=MODEL, max_tokens=300,
        messages=[{"role":"user",
                   "content": JUDGE_PROMPT.format(q=q, a=a)}])
    return json.loads(r.content[0].text)
注意:LLM-as-judge 不是真理,它本身也會出錯.它的價值在於把"無法量化的質量"變成"大致可追蹤的數字",讓你能比較不同版本的好壞,而不是給出絕對的裁決.
DAY 4

串成自動化評估流水線

~90 min

把前三天的零件串成一條可重復執行的流水線(pipeline):讀數據集 -> 跑 agent -> 算確定性指標 + judge 打分 -> 產出報告.改完 prompt 就重跑一次,用數字判斷有沒有變好.

DAY 5

寫成案例,讓人看見

~90 min

最後一步,也是回報最高的一步.把整個項目寫成一份 README / 案例,重點不是炫耀它多能幹,而是老實描述它會怎麼失敗,你又是怎麼處理的.這份文檔本身就是你求職和接單的武器.

✓ 本週完成標準

你有了一個帶完整評估流水線的手寫 agent,能用數字說明它的質量,還有一份老實描述失敗模式的案例文檔.你已經走在大多數"會寫 prompt 但不會評估"的人前面了.

產物:公開的 GitHub 倉庫 + 評估報告 + 案例 README.這是你的"手寫版"基準線(baseline).
WEEK 05

遷移到框架(對照組)

本週目標(延伸模塊)

把前四週手寫的物流 agent,用業界標準框架重做一遍.目的不是學 API,而是親身對比:框架幫你省了什麼,又把什麼藏了起來.做完你會有一個極有說服力的作品--"同一個 agent,我手寫和框架兩種都做過,而且能說清楚什麼時候該選哪個".

版本提醒:LangChain 和 LangGraph 已於 2025 年 10 月發布 1.0,官方承諾在 2.0 之前不再有破壞性變更(breaking changes),所以現在學是個穩定的好時機.動手時記得鎖定版本(pip install "langchain>=1,<2" "langgraph>=1,<2" langsmith langchain-openai),並以官方最新文檔為準--框架的 API 還是比裸 SDK 更新得快.接 DeepSeek:DeepSeek 走 OpenAI 兼容格式,所以這裡用 langchain-openai,把 base_url 指向 https://api.deepseek.com 即可(下面代碼示範).
DAY 1

用 create_agent 重建第二週的 agent

~90 min

先感受一下框架"搭建層"的威力:第二週你手寫了整個 agent loop 和 tool dispatch,在這裡幾行就搞定.重點是數一數到底省了多少行.

langchain 版 - 對比第二週那整個 loop 
from langchain.agents import create_agent
from langchain.tools import tool
from langchain.chat_models import init_chat_model

@tool
def track_shipment(tracking_no: str) -> dict:
    """查詢物流狀態"""
    return {"status": "in_transit", "eta_days": 2}

# DeepSeek 走 OpenAI 兼容格式:用 openai provider + base_url 指向 DeepSeek
model = init_chat_model(
    "deepseek-v4-flash", model_provider="openai",
    base_url="https://api.deepseek.com",
    api_key="sk-...",   # DeepSeek key(建議用環境變量)
)
agent = create_agent(
    model=model,
    tools=[track_shipment, calc_shipping_fee, check_inventory],
)
agent.invoke({"messages": [{"role": "user",
                            "content": "查 SF123 狀態"}]})
DAY 2

用 LangGraph 拿到"重啟後能接著跑"

~2 hr

把 agent 表達成一張狀態圖(state graph),並掛上檢查點(checkpointer).這帶來一個你手寫版沒有的能力:流程跑到一半服務器重啟了,也能從斷點接著跑.這是框架真正值錢的地方之一.

langgraph 版 - 狀態圖 + 持久化 
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

builder = StateGraph(AgentState)
builder.add_node("model", call_model)
builder.add_node("tools", run_tools)
builder.add_conditional_edges("model", should_continue)  # 分支
builder.add_edge("tools", "model")                    # 循環

graph = builder.compile(checkpointer=InMemorySaver())
# 同一個 thread_id:重啟後可從斷點接著跑,也支持人工審查中斷
graph.invoke(inp, config={"configurable": {"thread_id": "order-42"}})
DAY 3

用 LangSmith 換掉手寫的可觀測性

~60 min

第三週你手寫了結構化日誌.在這裡你會發現:只要設兩個環境變量(environment variable),LangSmith 就自動把每次調用的完整追蹤(trace),token,成本,延遲都記下來並可視化.對比一下你手寫那段 vs 開箱即用.

啟用追蹤 - 不用改任何 agent 代碼

# 跑 agent -> 到 LangSmith 後台看完整的 trace 樹,token,成本,延遲

langsmith 版評估 - 對比第四週手寫的 run_eval.py 
from langsmith import evaluate, Client

def correctness(run, example):       # 確定性 sensor
    return {"key": "correct",
            "score": run.outputs == example.outputs}

results = evaluate(
    lambda x: agent.invoke(x),
    data="logistics-evalset",        # 第四週那份數據集
    evaluators=[correctness, llm_judge],  # 確定性 + 推理式
)
